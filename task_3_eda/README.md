# 3\. Переход на Event-Driven-архитектуру

## Текущие проблемы и риски

### Взаимодействие ins-comp-settlement и ins-core-app

*\> сервис ins-comp-settlement раз в сутки осуществляет запрос в core-app по REST API для получения всех оформленных за день страховок.*

Обработка запроса core-app может занимать продолжительное время (несколько минут). Соответственно, может сработать таймаут на стороне ins-comp-settlement (т.е. **ins-comp-settlement решит, что core-app завис и не дождётся ответа**).

core-app явно делает к БД тяжёлые запросы, а в нашем Postgres может быть выставлен **таймаут на максимальное время обработки запроса на стороне сервера БД.**

Та реплика БД Postgres, из которой core-app будет запрашивать данные о всех страховках за день, будет на несколько минут **перегружена длительными аналитическими запросами от core-app.** Соответственно, пропускная способность всех core-app, которые к нему подключаются, может упасть в разы (пока у нас одна реплика Postgres, это может быть особенно неприятно).

Сам экземпляр core-app, к которому будет подключаться ins-comp-settlement, скорее всего, особой перегрузки не испытает: там явно используется неблокирующая обработка запросов.

#### Дополнительный риск на перспективу

В будущем объём сохраняемой и передаваемой информации может значительно вырасти (на порядок). Так как мы, скорее всего, захотим передавать партнёрам информацию не только о том, какие страховки были фактически куплены через нас, но и **сведения о том, какие предложения показывали посетителям по компаниям-конкурентам в нашем агрегаторе.** Так как клиентские анкеты к нашим партнёрам и так попадают, и если мы им не передадим все предложения по этим анкетам – партнёры начнут собирать информацию по предложениям конкурентов через наш агрегатор через подставные аккаунты, устроив нам невольную DDoS-атаку.

### Взаимодействие ins-core-app и ins-product-aggregator

Сервис core-app осуществляет запрос к ins-product-aggregator раз в 15 минут, а ins-comp-settlement — раз в сутки (ночью), при формировании реестра оформленных страховок.

core-app у нас запущен в нескольких экземплярах, которые работают с одной схемой Postgres. Это нормально, но нужна дополнительная логика, чтобы избежать конфликтов, когда сразу несколько экземпляров core-app пытаются записать в БД информацию об актуальных тарифах по страховкам, полученным от ins-product-aggregator. Или нужна дополнительная логика, чтобы запросы к ins-product-aggregator делал только один экземпляр core-app, а остальные просто подгружали обновления из Postgres, когда они там появятся.

Есть ли у нас с партнёрами SLA для их API, что от нас точно не прилетят 10 запросов одновременно от каждого экземпляра core-app – я не знаю. Если такое есть, то точно надо реализовывать логику, что запрос делает только один экземпляр core-app.

Как устроена обработка запроса внутри ins-product-aggregator – это я тоже не знаю. Но: по условию задачи, API партнёров изобильно предоставляет нам ошибки и задержки. Стало быть, при общении с API партнёров нам нужны:

* возможность ждать ответа долго (до нескольких минут);  
* возможность делать 2-3 повтора, причём с увеличивающимся таймаутом (например, 1 минута, 3 минуты, 5 минут);  
* корректная обработка частично успешных запросов (т.е. когда API 4 страховых компаний вернули обновление, а 5-е партнёрское API зависло, то core-app должно обновить у себя инфу по тем API, что доступны, а по зависшей страховой компании какое-то время пользоваться старой информацией).

В рамках синхронного HTTP-запроса такое делать действительно крайне неудобно \= )

### Проблемы ins-comp-settlement

ins-comp-settlement точно не перегрузит ничьё API, но есть проблема: core-app получает информацию о тарифах по одному расписанию (раз в 15 минут), а ins-comp-settlement по другому расписанию (раз в сутки). **И при подготовке ежемесячного отчёта будут рассогласования в данных с core-app** (core-app уже начал продавать страховки по цене со скидкой, а ins-comp-settlement в отчёте будет отмечать им цену без скидки, т.к. инфа о новой цене до него дойдёт только на следующий день).

Реальная задержка данных в ins-comp-settlement по сравнению с core-app может быть ещё дольше, если обновить данные ночью не удалось (например, ночью у какого-то из партнёров их API вообще отключилось, а починили его только утром, и ins-comp-settlement данные не обновило, а core-app обновило).

## Вариант решения

Для решения этих проблем в EDA-подходе нам нужно будет:

- развернуть очередь (kafka или RabbitMQ);  
- развернуть airflow;  
- доработать core-app, вынести логику ins-product-aggregator и ins-comp-settlement на airflow.

### ins-product-aggregator

ins-product-aggregator заменяем на airflow-DAG, где каждый оператор будет запрашивать обновления у своей компании-партнёра – и отправлять результат в очередь событий (для каждой компании 2 топика: по успешным запросам и по неуспешным запросам). Также результат сохраняется в Postgres-БД ins-product-update-db

Операторы параллельные, один оператор работает независимо от другого. Логику retry и timeout перекладываем на airflow. DAG должен запускаться каждые 15 минут.

Данные в очереди храним минимум месяц.

### core-app

Каждый экземпляр подписываем на топики обновлений по всем страховым компаниям, актуальный список продуктов и цен по страховым компаниям храним в памяти, в БД его не пишем.  
При старте нового экземпляра core-app читаем топики страховых компаний за последний месяц, берём оттуда последнее обновление продуктов для каждой компании.

### ins-comp-settlement

ins-comp-settlement тоже можем выполнить в виде airflow-DAG, для каждой компании отдельный task group со следующими операторами:

- выбрать из БД успешные обновления по этой компании за расчётный месяц (из схемы обновлений по продуктам), заодно и проверить, что обновления там точно есть;  
- сформировать сам отчёт по компании-партнёру;  
- отправить его в компанию-партнёр.

Каждый task group запускаем параллельно, операторы в task group идут последовательно.

### Зачем airflow?

Почему стоит перевести задачи по расписанию на airflow? Потому что это из коробки даёт хорошую наблюдаемость и хорошую поддержку частично успешных сценариев (когда часть операторов корректно отработала, а часть нет). 

Также весьма удобно смотреть логи именно от упавших операторов, чтобы понять, что с ними не так. И не нужно думать про самопальный Web UI с кнопкой перезапуска \= )
