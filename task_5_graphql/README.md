## Существующее REST API

Декларация REST API: [`current_contract.openapi.yaml`](customer_service_graphql/current_contract.openapi.yaml)

### Какие там основные сущности?

REST API предоставляет доступ к трём основным сущностям:

**1. Client (Клиент)** - основная сущность
- `id` - уникальный идентификатор клиента
- `name` - ФИО клиента
- `age` - возраст клиента
- Эндпоинт: `GET /clients/{id}`

**2. Document (Документ клиента)**
- `id` - уникальный идентификатор документа
- `type` - тип документа (паспорт, водительские права и т.д.)
- `number` - номер документа
- `issueDate` - дата выдачи
- `expiryDate` - дата окончания действия
- Эндпоинт: `GET /clients/{id}/documents` - возвращает массив документов

**3. Relative (Родственник клиента)**
- `id` - уникальный идентификатор родственника
- `relationType` - тип родства (супруг, ребёнок, родитель и т.д.)
- `name` - ФИО родственника
- `age` - возраст родственника
- Эндпоинт: `GET /clients/{id}/relatives` - возвращает массив родственников



### Какие там подводные камни?

Там показан один из случаев underfetching (недостаточной выборки данных): если нам понадобится не просто имя и возраст клиента, а ещё его документы и родственники, то нам нужно делать 3 запроса вместо 1.

Кроме того, если набор данных будет действительно широким (до 500 полей), то можно получить одновременно и overfetching (т.е. загрузку данных, которые клиенту не нужны, что будет влиять на производительность);

Если к этому API будут обращаться разные клиенты, которым нужен разный набор данных, то это опасно.

### Как можно решить проблему, оставаясь в рамках REST API?
В таких случаях можно остаться в рамках REST API, но придётся реализовывать механизм неполной загрузки данных:
  - делаем декларацию, что в возвращаемом типе данных у нас есть не только `required`-поля, но и такие поля, которых в возвращаемой JSONке может вообще не быть;
  - начинаем передавать на вход наших REST-методов объекты с настройками неполной загрузки данных (какие поля загружать для родительских объектов, какие поля загружать для вложенных объектов), классы настроек неполной загрузки данных обязательно вносим в OpenAPI-декларацию;
  - у и далее реализуем неполную загрузку данных (тут всё равно придётся поработать руками, даже если мы сидим на GraphQL);

Если у нас будет Python + FastAPI + Pydantic 2, то можно достаточно просто сгенерировать и правильную OpenAPI-декларацию возвращаемых типов данных в FastAPI (указывая необязательным полям в pydantic правильные метаданные). Если немного заморочиться, то можно и генерировать правильные pydantic-классы для настроек неполной загрузки.

## Зачему нужно GraphQL API?

Нас интересует сценарий, когда наше API будет:
- работать поверх широких таблиц данных в БД (до 500 полей);
- получать запросы на поиск разных наборов данных даже в рамках одной сущности (например, мы выбираем клиентов нашего страхового агрегатора, но для разных целей нам нужны разные наборы полей. Например, нам нужен выбор: загружать документы клиентв / не загружать документы клиента, загружать год рождения / не загружать год рождения);
- иногда -- выдавать данные многократной вложенности (например, "Клиент страхового агрегатора" --> Родственники --> "Ранее оформленные страховки" --> "Страховая компания")

Какие есть плюсы по сравнению с самопальными настройками неполной загрузки:
- это более стандартное решение, чем городить свои собственные классы настроек неполной загрузки данных;
- не нужно возиться с тем, чтобы правильно включить их в OpenAPI-декларацию;
- из коробки будет доступен механизм подписок (может неплохо помочь, если данные по запросу клиента будут поступать постепенно, как предложения от разных страховых компаний);

Тонкости
- крайне желательно делать батчинг данных в Data Loader'ах (хотя бы на мало-мальски популярные запросы верхнего уровня);
- в любом случае нужна профилировка запросов, т.к. запросы могут быть очень разными!;
- и нужно отдельно проверять, что у юзера есть доступы к тем данным, которые он запрашивает.


### Что у нас в `customer_service_graphql`?

В директории [`customer_service_graphql/`](customer_service_graphql/) я склепал простенький пример GraphQL API сервис для просмотра клиетнов страхового агрегатора.

#### Основные файлы

**1. [`models.py`](customer_service_graphql/models.py)** - SQLAlchemy-модели данных
- Определяет структуру БД (SQLite)
- Три основные модели: `Customer`, `Document`, `Relative`
- Расширенные поля (email, phone, credit_score, is_verified и др.)
- Функция `populate_sample_data()` для генерации тестовых данных
- Async SQLAlchemy для неблокирующих запросов

**2. [`main.py`](customer_service_graphql/main.py)** - Приложение на FastAPI + Strawberry GraphQL
- GraphQL-типы: `Customer`, `Document`, `Relative` с опциональными полями
- **Селективная загрузка полей** - из БД загружаются только запрошенные поля
- **DataLoader** для батчинга запросов (решение проблемы N+1 запроса к БД)
- Query: `customer(id)`, `customers(ids)`
- Mutation: `createCustomer(input)`
- Subscription: `ticker()` (демонстрационная)
- Поддержка `snake_case` для имён полей

**3. [`schema.graphql`](customer_service_graphql/schema.graphql)** - GraphQL-схема в SDL формате
- Автоматически генерируется из Strawberry-типов
- Доступна по эндпоинту `GET /schema.graphql`
- Описывает все доступные типы, запросы и мутации

**4. [`schema.json`](customer_service_graphql/schema.json)** - GraphQL-схема в JSON-формате
- Результат introspection query
- Доступна по эндпоинту `GET /schema.json`
- Используется инструментами для автогенерации клиентского кода

#### Как запустить

**Шаг 1: Инициализация БД**
```bash
cd customer_service_graphql
python models.py
```
Создаёт `customer_service.db` с тестовыми данными (5 клиентов с документами и родственниками).

**Шаг 2: Запуск сервера**
```bash
python main.py
```
Сервер запускается на `http://0.0.0.0:9001/graphql`

**Шаг 3: Тестирование**
Откройте в браузере `http://localhost:9001/graphql` - откроется GraphiQL интерфейс.

Пример запроса:
```graphql
query {
  customer(id: 1) {
    id
    name
    email
    documents {
      id
      type
      number
    }
  }
}
```

#### Ключевые особенности реализации

**Селективная загрузка полей:**
- Анализ GraphQL запроса через `info.selected_fields`
- Использование SQLAlchemy `load_only()` для загрузки только нужных колонок
- Логирование запрошенных полей для отладки

**DataLoader для оптимизации:**
- `load_documents_by_customer()` - батчинг загрузки документов
- `load_relatives_by_customer()` - батчинг загрузки родственников
- Решает проблему N+1 запросов при загрузке вложенных данных

**Опциональные поля:**
- Все поля (кроме `id`) опциональны в GraphQL-типах
- Поддержка частичной загрузки данных
- Клиент сам решает, какие поля ему нужны

Подробная документация: [`customer_service_graphql/README.md`](customer_service_graphql/README.md)


#### GraphQL-декларация

Полная схема: [`schema.graphql`](customer_service_graphql/schema.graphql)

**Основные типы:**

**1. Customer** - клиент страхового агрегатора
```graphql
type Customer {
  id: Int!                      # обязательное поле
  name: String                  # опциональное
  age: Int                      # опциональное
  email: String                 # ← новое поле
  phone: String                 # ← новое поле
  credit_score: Int             # ← новое поле (кредитный рейтинг)
  is_verified: Boolean          # ← новое поле (прошёл ли верификацию)
  documents: [Document!]!       # вложенный список документов
  relatives: [Relative!]!       # вложенный список родственников
}
```

**2. Document** - документ клиента
```graphql
type Document {
  id: Int!
  customer_id: Int
  type: DocumentType            # enum: PASSPORT, DRIVERS_LICENSE, и т.д.
  number: String
  issue_date: Date
  expiry_date: Date
  issuing_authority: String     # ← новое поле (орган выдачи)
  is_verified: Boolean          # ← новое поле (прошёл ли проверку)
  scan_url: String              # ← новое поле (URL скана)
}
```

**3. Relative** - родственник клиента
```graphql
type Relative {
  id: Int!
  customer_id: Int
  relation_type: RelationType   # enum: SPOUSE, CHILD, PARENT, и т.д.
  name: String
  age: Int
  phone: String                 # ← новое поле
  is_dependent: Boolean         # ← новое поле (является ли иждивенцем)
  income_contribution: Float    # ← новое поле (вклад в семейный доход, %)
}
```

**Что изменилось по сравнению с REST API:**

1. **Расширенные поля моделей:**
   - `Customer`: добавлены `email`, `phone`, `credit_score`, `is_verified`
   - `Document`: добавлены `issuing_authority`, `is_verified`, `scan_url`
   - `Relative`: добавлены `phone`, `is_dependent`, `income_contribution`

2. **Вложенные связи и точечные запросы:**
   - В REST API: 3 отдельных запроса (`/clients/{id}`, `/clients/{id}/documents`, `/clients/{id}/relatives`)
   - В GraphQL: один запрос с вложенными полями `documents` и `relatives`, а также отдельные запросы `document(id)` и `relative(id)`

3. **Опциональность полей:**
   - Все поля (кроме `id`) опциональны - поддержка селективной загрузки
   - Клиент запрашивает только нужные поля, остальные не загружаются из БД

4. **Типизированные enum'ы:**
   - `DocumentType`: PASSPORT, DRIVERS_LICENSE, EMPLOYMENT_CERTIFICATE, INCOME_CERTIFICATE, OTHER
   - `RelationType`: SPOUSE, CHILD, PARENT, SIBLING, GUARDIAN, BENEFICIARY

5. **Единая точка входа:**
   - Query: `customer(id)`, `customers(ids)`, `document(id)`, `relative(id)` - получение данных
   - Mutation: `create_customer(input)` - создание клиента
   - Subscription: `ticker()` - демонстрация real-time обновлений

6. **Использование `snake_case`:**
   - Все поля в `snake_case` (настроено через `NameConverter(auto_camel_case=False)`)
   - Соответствует Python-стилю кодирования
