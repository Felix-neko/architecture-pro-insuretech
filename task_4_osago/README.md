# 4\. Проектирование продажи ОСАГО

## Контекст и проблемы

Наши партнёры могут выставить нам SLA по обращению к их API (по общему RPS и по скачкам). Соответственно, нужно как-то ограничивать исходящий RPS (иметь свои настройки для каждого партнёра).

По интеграции с фронтэндом – требуется динамически обновлять состояние фронтэнда по мере поступления результатов.

API партнёров может быть нестабильным, частично успешные случаи нужно корректно отрабатывать.

Сервис core-app не слишком производителен, сценарий “клиент переодически опрашивает бэк” может его значительно перегрузить.

Наш сервис core-app всё равно не очень производительный, нам нужно уметь ограничивать не только общую нагрузку, но и нагрузку на каждый из его подов (иначе можем поймать ситуацию, когда поды core-app постоянно перезагружаются, и как только один из них выйдет из перезагрузки, то ловит на себя всю нагрузку, падает и уходит в перезагрузку обратно).

### Интеграция фронтэнда и core-app

Чтобы не перегружать core-app поллингом, используем подход Server Push.

* Фронтэнд отправляет анкету ОСАГО в core-app.  
* core-app возвращает клиенту id его зарегистрированной заявки (действует только для клиента и определённое время).  
* По этому id заявки фронтэнд подписывается на GraphQL Subscription, где ему будут сыпаться обновления от core-app:  
  * у каких страховых компаний мы будем запрашивать предложения;  
  * какие страховые компании нам уже прислали предложения;  
  * какие страховые компании отказали;  
  * с какими страховыми компаниями не удалось связаться (даже после всех повторных попыток).

Если неохота работать с GraphQL (например, под Kotlin нет подходящих библиотек), можно сделать взаимодействие и через вебсокет. Но лучше GraphQL, чтобы получить готовую сериализация и проверку схемы из коробки.

### osago-aggregator и его интеграция с core-app

При получении заявки с анкетой ОСАГО core-app создаёт события в очереди (топики “новые анкеты ОСАГО” для каждой поддерживаемой страховой компании).

После чего core-app подписывается на несколько топиков по id своей заявки (по топику для страховой компании) и делает асинхронное ожидание, пока в топиках будут появляться данные (предельное ожидание 60 секунд).

Далее, нам нужно реализовать паттерн competing consumers по каждой страховой компании:

* по каждой страховой компании работает отдельный Deployment из нескольких osago-aggregator (HPA в зависимости от числа необработанных заявок в очереди);  
* каждый Deployment запускает свои экземпляры osago-aggregator с определённой настройкой (для какой страховой компании ему нужно формировать запрос);  
* в рамках каждого Deployment экземпляры osago-aggregator извлекают заявки из топика своей страховой компании и делают запрос к API страховой компании-партнёра, о чём сообщаем в топик (событие типа “обработка заявки начата”);  
* при ответе API партнёра – пишем в топик событие типа “обработка завершена” с предложением или сообщением об отказе;  
* при неответе API партнёра или HTTP-ошибке – пишем в топик служебное сообщение об ошибке;  
* каждый Deployment работает со своим API партнёра через Egress Gateway с отдельными настройками по RPS и max burst, при превышении RPS или max burst запрос должен не обрываться, а задерживаться.

Очередь сообщений здесь попробуем реализовать через Redis Streams, там обещали удобный механизм динамического создания большого количества временных топиков (под конкретные заявки), а также хорошую поддержку consumer groups \+ PEL \+ XCLAIM/XAUTOCLAIM.

Важно: стоит складывать в БД не только данные о проданных страховках (это core-app \+ и так делает): предложения по заявкам ОСАГО, полученным от партнёров, тоже стоит складывать в БД для последующего анализа. Главное – сразу предусмотреть возможность параллельной записи при выборе схемы данных.
